## Everyday workflow

1. Run Quick Scan or Deep Research (including Guided Research preferences).
2. Open **Product Review Center**. A card appears immediately; filters and historical research-session/individual-collection selectors are expandable. Review one product, or switch to Overview Mode for a searchable sortable table grouped by scan or rating.
3. Rate **Love it**, **Like**, **Maybe later**, **Pass** or **Unrated**. Love/Like populate My Favorites; Maybe later populates the watchlist; Pass hides a product from the default queue without deleting evidence. Notes are under My notes. Ratings and notes can be changed at any time.
4. Previous, Next and Skip move through the queue; the cursor is saved for Resume Review. Optional Ctrl+Shift+1–4 rating shortcuts are guarded while an input or notes editor has focus. Preferences remain separate from opportunity scores and match reviews.
5. Open evidence, observations or monthly scenarios as needed. Monthly revenue is assumed selling price × assumed units; monthly contribution is modeled unit contribution × assumed units. Conservative/base/optimistic quantities, selling price and ad cost can be edited and saved. These are hypothetical scenarios, not demand forecasts. Incomplete economics stay unknown.
6. Open **My Favorites**, choose products or use all favorites, and expand the export wizard. Download the research workbook, or review/edit selling prices before generating Shopify CSV. CSV downloads stay disabled if no eligible rows remain. Draft is the default; even the optional active status remains unpublished in the CSV.
7. Read the validation report. Missing prices always exclude a row. Other incomplete verification excludes rows by default; you can explicitly include them as drafts for manual work. Images without reuse permission and unverified/copyrighted descriptions are omitted. Cost per item is included only for matching store currency and a verified non-minimum quote. No conversion, inventory availability or fulfillment service is invented.

## Settings and credentials

General preferences cover market, currency, business model, default scan mode and permitted images. Research preferences control query/source/product limits, category inclusion/exclusion, presets and reuse of successful collections (0–900 seconds). Collection concurrency is explicitly fixed at one to preserve existing isolation and rate limits. Financial assumptions centralize fees, fulfillment expenses, duties, tax, returns, advertising, conversion assumptions, budget and contribution targets; named scenarios and reset controls are provided.

Sources retain their real access status and errors. Best Buy supports explicit browser/API preferences and automatic choice based on credentials. Browser-first falls back to the official API only when Chromium is unavailable; access barriers and rate limits never trigger attempts to bypass restrictions. API-only requires an actual key. Entering a key is never considered proof of successful integration.

Windows Credential Manager stores supported Best Buy and Google Ads credentials under provider-scoped targets for the current Windows user. Credentials are never prefilled into the browser or copied into SQLite. UI fields are password masked; status displays only configured/not configured. Environment credentials are retained for existing deployments; explicit legacy session credentials still work. Google Ads requires the provider's official OAuth setup and a refresh token; the app does not invent an OAuth enrollment flow. CJ/eBay credential entry is deliberately unavailable because their connectors are not implemented. Connection tests issue bounded read-only requests and save only redacted results. Neither authenticated Best Buy API access nor Google OAuth access could be live-tested without the user's actual credentials.

Security and Diagnostics shows version/runtime, configured localhost binding, safe source diagnostics, audit commands and a consistent downloadable SQLite backup. The active data directory is displayed; changing POF_DATA_DIR requires restarting and intentionally managing the old data. No automatic move or overwrite is performed. Raw logs/provider responses and credential values are not displayed.

## Persistence and recovery

Migration 3 adds candidates, listings, observations, scan_products, product_ratings, product_notes, favorites and investigations. Listings retain the original snapshot identity; canonical review candidates use source-specific SKU where present plus known variant/model/GTIN evidence. Similar titles never merge preferences across merchants. More specific newly available identity evidence can conservatively create a separate candidate rather than silently transferring a rating. Observations reference original immutable snapshots, which retain prices, shipping, currency and collection timestamps. Aggregate research sessions remain in the existing config table and are associated with candidate investigations.

Before migration, SQLite's backup API writes a sibling `*.pre-review-v3.*.sqlite3` file including committed WAL contents. Schema changes/backfill run in a transaction; failure rolls back and does not substitute an empty library. Keep the backup private. To recover, stop the application, preserve the current database and its companion files, and restore a known-good backup to the intended data directory. Relaunch and verify history and ratings before discarding the preserved copy. Downloaded backups restore as standalone SQLite files; this was tested with saved notes and favorites.

Existing licensed observation expiry remains enforced, including derived session economics. Ratings/notes survive expiry; unavailable evidence is identified separately instead of retaining expired product payloads. Offline backups/exports require the owner's retention management, as before.
